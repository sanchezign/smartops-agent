# Security audit before publication (2026-10)

Final security audit of SmartOps Agent before the repository goes public on GitHub and before the
code is offered to real clients (SMBs that connect their WhatsApp Business number). Read-only:
nothing in the code, the history or the servers was changed. The fixes are proposed at the end as
small pull requests, to be approved one by one.

- **Date:** 2026-10-09. **Audited revision:** `main` at `eb58e1e` (v0.17.0 + one fix), plus every
  branch and tag of `origin` for the history part.
- **Scope:** the eight areas the owner asked for: (1) data that must not become public, in the
  whole git history; (2) authentication and sessions; (3) authorization; (4) untrusted input;
  (5) demo mode; (6) infrastructure and supply chain; (7) logs and privacy; (8) public
  documentation.
- **Method:** manual code review of `apps/api`, `apps/admin`, `deploy/`, `.github/`, `docker/`,
  `n8n/` and the docs, plus automated scans of the history (below). Every finding was traced from
  a real entry point to the code that misbehaves.
- **Limits:** the audit is static. The test suites could not be run in the audit sandbox (it has
  Node 22, the project needs Node 24 for `crypto.argon2`, and the network policy blocks
  `cdn.sheetjs.com`, from which `xlsx` is installed); CI runs them on every change. The live demo
  server, the OCI console and the GitHub repository settings were not inspected (no access): the
  items that depend on them are listed as owner checks.

## Summary

No secret, key or token was found anywhere in the history: the repository can be published
without rewriting history. One open question must be answered first (F-02: a phone number in the
tests that does not follow the fake-number pattern). The most important finding is not about
publication but about selling the product: **any WhatsApp user can take over an existing
supplier's identity by writing that supplier's name on a price list** (F-01). It must be fixed
before a real client.

## 2. Findings

### F-01 — An unknown contact is linked to an existing supplier by the name on its document (High)

**Evidence.**

- `apps/api/src/modules/catalog/supplier-resolution.ts:40-75` — when the sending contact has no
  supplier yet, the `supplierName` that the model extracted **from the document itself** is
  matched against existing suppliers; exactly one match → the contact is linked to that supplier
  (`tx.linkContact`, line 73) and only an informative warning `supplier_linked` is recorded.
- `apps/api/src/modules/catalog/catalog-ingest.service.ts:155-215` — the plan is then computed and
  applied in the same transaction, against **that supplier's catalog**. `planIngestion` does not
  know that the link was created a moment ago.
- `apps/api/prisma/schema.prisma:361` — a new WhatsApp contact has `kind = unknown`;
  `apps/api/src/modules/extraction/prefilter.ts:155` only diverts `customer` contacts, so a
  stranger's message is classified and extracted like a supplier's.
- `apps/api/src/modules/settings/settings.schemas.ts:43-54` — price changes up to +50 % / −30 % per
  list are applied without review, and `catalog.autoCreateProducts` adds new products.
- `apps/api/src/modules/catalog/ingest-plan.ts:207` — the threshold is relative to the CURRENT
  price, so repeated lists compound (−30 % per message).

**Impact.** On a real deployment anybody who can send a WhatsApp message to the business number
(the number is public: customers write to it) can send an image or PDF that says
"Distribuidora Norte S.A. — price list" and:

1. become, permanently, a contact of the real supplier "Distribuidora Norte" (later lists from the
   attacker's number are attributed to it without any name check);
2. change that supplier's prices by up to −30 % / +50 % per message, without review, and repeat;
3. add products to that supplier's catalog.

The team gets a price-change alert (over `catalog.priceAlertPct`), but only after the catalog was
changed, and the catalog is what the business quotes from. This breaks the product's central
promise ("never guesses; anything doubtful goes to a person").

**Exploitability.** Easy: no account, no credential, only a WhatsApp number and the name of a
supplier (often printed on the client's invoices or website). Not exploitable on the public demo
(no real WhatsApp: the demo only injects its own samples).

**Fix (PR "fix(catalog): never link an unknown contact to an existing supplier automatically").**
When the contact is not linked yet and the document's name matches an existing supplier, create
the `unknown_supplier` gate (scope `run`, admin only) with the candidate instead of linking. Linking
a new number to an existing supplier is an identity decision for a person. Keep the automatic
creation of a NEW supplier only behind F-03's setting. Integration test: an unlinked contact
naming an existing supplier ends in `needs_review`, prices untouched; the approved gate links it.
Record the rule in a new ADR (it amends the "user rule 2026-09-25" of ADR-012).

### F-02 — A phone number that may be real, in code and tests since the first webhook commit (Medium, pending confirmation)

**Evidence.** A Uruguayan mobile number (masked here as `598*****160`, the repository's own mask) appears since commit `be06c1c` (2026-09-24,
"add whatsapp webhook verification and signed event capture") and is in HEAD:

- `apps/api/src/common/phone.ts:3` (doc comment of `maskPhone`);
- `apps/api/test/unit/phone.test.ts:18,34`;
- `apps/api/test/fixtures/heuristics-es-corpus.json:632,918` (generated corpus).

Every other number in the repository follows the documented fake patterns (`59899000111`,
`59899123456`, `59899000xxx`, `15550000000`…); this one does not. It may be the author's number or a
real test recipient.

**Impact.** If it is real, a personal phone number becomes public and indexed together with the
author's name and e-mail (commit metadata). If it is invented, there is nothing to do beyond
replacing it for consistency.

**Fix.** The owner confirms whether it is real.

- Invented → replace it in HEAD with `59899000123`-style fakes (PR "test: fake phone numbers
  only"), not blocking.
- Real → it is personal data in 8 commits. The owner rule is "never rewrite history"; the options
  are (a) accept it, (b) rewrite history once before the first public push (`git filter-repo
--replace-text`, then force-push every branch and tag — a decision only the owner can take), or
  (c) publish a fresh repository from a squashed snapshot. This audit does not recommend one over
  another; it only blocks publication until the owner decides.

### F-03 — Unknown contacts create suppliers and products automatically and spend the AI budget (Medium)

**Evidence.** `supplier-resolution.ts:64-72` creates a new supplier for any contact whose list names
no existing supplier (`supplierName`, else the WhatsApp profile name); with
`catalog.autoCreateProducts = true` (default) every line becomes a product. The AI caps are per
contact (`AI_DAILY_LIMIT_PER_CONTACT`, 20) and global (`AI_DAILY_BUDGET_USD`, 0.50) —
`apps/api/src/config/env.ts:264-270`.

**Impact.** Spam suppliers and products in the client's catalog; a handful of numbers can spend the
daily AI budget, after which the real suppliers' lists stop being processed automatically until
the next UTC day (availability, not integrity).

**Exploitability.** Easy (only WhatsApp numbers). Not on the demo.

**Fix (with F-01).** A setting `catalog.autoCreateSuppliers` (default `false` for client
deployments, `true` in DEMO_MODE) that turns "new sender + price list" into an `unknown_supplier`
gate; optionally a global cap of AI calls per day for contacts not linked to a supplier, so
strangers can never take the whole budget.

### F-04 — Next.js 15.5.26 with three medium advisories (Medium)

**Evidence.** `apps/admin/package.json:21` pins `next` 15.5.26. Renovate opened
[sanchezign/smartops-agent#48](https://github.com/sanchezign/smartops-agent/pull/48) (15.5.27) for
GHSA-mcj8-r9mp-w47p and GHSA-4jqv-mc3x-m676 (cache poisoning of SSG / ISR routes, the first one with
a root-level catch-all page) and GHSA-f87g-xv8r-7p7x (metadata image routes). The panel has a
root-level catch-all, `apps/admin/src/app/(main)/[...rest]/page.tsx`.

**Impact / exploitability.** Probably not exploitable here: the panel renders per request (the
language comes from a cookie) and has no metadata image routes, but that was not proven, and the
update is a patch release.

**Fix.** Merge #48 (the owner merges; Renovate never automerges) before publishing.

### F-05 — The panel sends no security headers of its own (Medium)

**Evidence.** `apps/admin/next.config.ts` defines no `headers()`. CSP, `frame-ancestors`, HSTS,
`X-Frame-Options`, `nosniff`, `Referrer-Policy` and `Permissions-Policy` are set only by
`deploy/Caddyfile:23-36`. The API has `helmet()` (`apps/api/src/app.ts:91`), the panel does not.

**Impact.** The public demo is protected (it runs behind Caddy). A client deployment without that
Caddyfile — the documented "option A" (Vercel rewrite), a different reverse proxy, or a panel
reached directly on port 3000 — serves the panel with no anti-framing header and no CSP:
clickjacking of operator actions (approve a review, reply to a customer) becomes possible.

**Fix (PR "feat(admin): security headers in the panel itself").** The same headers in
`next.config.ts` `headers()`, so they hold wherever the panel runs. Caddy already uses `?` for most
of them (set only if the upstream did not), so nothing is duplicated; HSTS and `nosniff` stay forced
at the edge.

### F-06 — No self-service password change (Medium for a client, not for the demo)

**Evidence.** `apps/api/src/modules/auth/auth.routes.ts` offers login, refresh, logout, logout-all
and `PATCH /me` (language only). Passwords are only set by an admin:
`POST /api/v1/admin/users` and `POST /api/v1/admin/users/:id/reset-password`
(`apps/api/src/modules/admin/admin.routes.ts:574-606`). There is no "must change password" flag.

**Impact.** On a client deployment every operator's password is chosen by — and stays known to —
the admin who created it; nobody can rotate their own password after a suspected exposure. With no
MFA yet (already listed as required before a client), the password is the only factor.

**Fix (PR "feat(auth): change your own password").** `POST /api/v1/auth/password` (Bearer, current

- new password, policy checked, other sessions revoked, audited) and a `mustChangePassword` flag set
  by admin create / reset and enforced by the panel. Refused for the public demo account, like the
  other shared-account actions.

### F-07 — Per-account lockout can keep a known account locked (Low)

**Evidence.** `apps/api/src/modules/auth/login-lockout.ts:122-167`: 5 failures in 15 minutes lock
the account (15 → 30 → 60 minutes, capped at 1 hour); the per-IP limit is 10 attempts per
15 minutes (`auth.routes.ts:59-65`), so one IP is enough to re-lock.

**Impact.** Someone who knows a user's e-mail (an admin's address is easy to guess) can keep that
person out of the panel indefinitely; an admin can unlock, the attacker re-locks. Integrity is not
affected. This is the documented OWASP trade-off (ADR-018), so it is low.

**Fix (before a client, together with MFA).** Do not count failures from a browser that already
logged in successfully as that user (a signed "known device" cookie), or lock per account + IP and
keep a slower global per-account delay; notify the user when the account is locked.

### F-08 — Media download follows redirects to any host (Low)

**Evidence.** `apps/api/src/modules/whatsapp/whatsapp-media.client.ts:124-142`: the allow-list
(`isAllowedDownloadUrl`) is checked for the first URL only, then `fetch` follows redirects with the
default `redirect: "follow"`. The `Authorization` header is dropped on a cross-origin redirect (fetch
spec), so the token is not exposed, but the request itself is made and its bytes are stored.
`graph-api.ts:76` has the same default.

**Impact / exploitability.** Needs a Meta host (or something answering as one) to send a redirect:
unlikely. If it happened, the worker would fetch an arbitrary URL from inside the server's network
(blind SSRF). `docs/security.md` states that "download URLs are only followed to Meta's hosts".

**Fix (PR "fix(api): no redirects outside Meta's hosts").** `redirect: "manual"` and re-check every
`Location` with the same allow-list (or `redirect: "error"` if Meta's downloads never redirect;
check with real traffic first, `docs/development.md`). Unit test with the fake Graph API answering a
redirect to another host.

### F-09 — The deterministic injection detector only covers spreadsheets (Low)

**Evidence.** `containsInjection` (`apps/api/src/modules/sheets/list-rules.ts:71`) runs only in the
spreadsheet path (`sheet-extraction.ts:347,412`, `sheets/fake-responders.ts`). Text messages,
captions, transcripts, PDF and image input depend on the model's own `suspiciousInstructions` flag
(`apps/api/src/modules/extraction/ingestion.service.ts:478-481`).

**Impact.** A text, a voice note or a PDF with an injection the model does not flag is processed
normally; the catalog rules (thresholds, gates) still apply, so the damage is bounded. The README
says "injection attempts stop for review", which is true only when one of the two detectors fires.
The prompt structure itself is sound: tags are neutralized after NFKC normalization
(`message-input.ts:27-38`), outputs are Zod-validated, and the internal API only takes ids
(`/internal/catalog/ingest { runId }`), so n8n or the model can never write catalog rows directly.

**Fix (PR "fix(api): the injection detector on every text input").** Also run `containsInjection` on
the message text, caption, transcript and converted document text before extraction, OR-ed with the
model flag. Cheap, deterministic, language independent.

### F-10 — The demo operator can re-link a contact through the column-mapping review (Low)

**Evidence.** ADR-030 lets the public operator approve `column_mapping` reviews in DEMO_MODE and
says "nothing else changes". But the approval body accepts `supplierId`
(`apps/api/src/modules/reviews/review.schemas.ts:21`), and for `column_mapping`
`review.service.ts:358-386` links the sender contact to that supplier — the identity decision that
is admin-only everywhere else (`unknown_supplier`).

**Impact.** Demo only: a visitor can attach a demo contact to another demo supplier until the next
reset (≤ 60 minutes). No effect on a real deployment (operators cannot resolve this review there).

**Fix.** In `resolveReview`, refuse `supplierId` / `createSupplier` from an operator who is only
allowed by the demo rule (403), and add that case to `authz-review-matrix`. Or document it in ADR-030
if the showcase needs it.

### F-11 — Visitors can post arbitrary text that other visitors see (Low)

**Evidence.** On the demo every visitor is the same operator (ADR-021); `POST
/api/v1/admin/conversations/:id/reply` (`admin.routes.ts:453-478`) accepts any text up to 4,096
characters, stored and shown to every visitor until the next reset (60 minutes,
`DEMO_RESET_INTERVAL_MINUTES`). React escapes it and no URL is turned into a link.

**Impact.** Not a code-execution risk; a reputational one: offensive text or a phishing URL on the
portfolio's front door for up to an hour. The global API limit (300/min per IP) does not prevent it.

**Fix (demo only).** In DEMO_MODE, replies from the public account: a tight global limit (for
example 10 per 10 minutes) and a shorter maximum length; or replace the free text with a few
canned replies in the demo.

### F-12 — OCI tenancy name, network layout and resource names in the docs (Low)

**Evidence.** `docs/history/phase-log.md:1064-1067` (the tenancy name, home region,
compartment `smartops`, budget, the reserved IP), `docs/history/phase-log.md:1096-1101`
(VM name, subnet, private IP, Bastion name and its allowlist policy),
`docs/deploy/keepalive.md:148`, and the same text in 8 commits (`bc4fc41`, `a032c59`, `87ca323`,
`6448075`… and their twins on other branches). `CLAUDE.md` also names the IAM user
`smartops-launcher`, still pending deletion in the OCI console.

**Impact.** The tenancy name opens the OCI sign-in page of that exact tenancy
(`cloud.oracle.com/?tenant=…`), which helps targeted phishing or password spraying against the
owner's cloud account. The IP is public through DNS already; the rest is reconnaissance detail.
None of it is a credential.

**Fix.** Redact in HEAD (PR "docs: redact cloud account details"): tenancy → `<tenancy>`, private
IP and Bastion name removed; keep the history (the owner's rule). Owner checks: MFA enabled on the
OCI console user, and delete the `smartops-launcher` IAM user, its API key, group and policy (already
in "Owner's checks"), before publishing.

### F-13 — App files writable by the app user; containers not read-only (Low)

**Evidence.** `apps/api/Dockerfile:47` and `apps/admin/Dockerfile:35` copy the application with
`--chown=node:node` and run as `node`; `deploy/compose.yaml` / `compose.light.yaml` set
`cap_drop: [ALL]` and `no-new-privileges` (good) but not `read_only`.

**Impact.** After a code-execution bug, an attacker could rewrite the app's own JavaScript and
persist until the container is recreated. Defense in depth only.

**Fix.** Copy as root-owned (`COPY --from=build /out ./` without `--chown`, the files stay readable),
and `read_only: true` with a `tmpfs` for `/tmp` on `api`, `admin` (check what Next's standalone server
writes, e.g. `.next/cache`) in the compose files; the local harness proves it.

### F-14 — The server runs scripts from an image pulled by a mutable tag (Low)

**Evidence.** `deploy/bin/fetch-bundle.sh:24-27` pulls `ghcr.io/sanchezign/smartops-api:<version>`,
checks only the `org.opencontainers.image.version` label, then `deploy.sh` executes the bundled
`deploy.sh` as root (`deploy.sh:43-47`).

**Impact.** Whoever can publish that tag (today: the `release` workflow on `main` with
`GITHUB_TOKEN`, or a stolen token with `packages:write`) gets root on the VM. This is the expected
trust chain of a pull model, but nothing verifies that the image came from that workflow.

**Fix (later).** Sign the images in `release.yml` (keyless cosign / GitHub artifact attestations,
already half-way with `provenance: mode=max`) and verify the signature, or the digest recorded in the
GitHub release, in `fetch-bundle.sh` before extracting. When the repository is public, also decide
the GHCR package visibility (public images make the VM's read token unnecessary).

### F-16 — Personal and operational data that will become public by design (Info)

- The author's full name and personal e-mail are in all 256 human commits (author and committer).
  Normal for GitHub; changing it needs a history rewrite. Future commits can use the GitHub
  `noreply` address if the owner prefers.
- `CLAUDE.md` and `docs/history/` describe the owner's workflow in detail: local paths
  (`C:/dev/smartops-portfolio-kit/`), dates when tokens and exceptions expire (GHCR read token
  2026-12-31), the open owner checklist. Not secrets; the owner may want to trim "Owner's checks" and
  "Dates that will bite" before publishing, since they tell a reader when the deployment is weakest.
- Test e-mails use real-looking domains (`ferreteria.uy`, `x.uy`); nothing is ever sent to them. The
  reserved `.test` / `.example` domains are preferable in new tests.

### F-17 — Defense-in-depth notes (Info)

- **Caddy deny list.** `deploy/Caddyfile:38-41` hides `/api/v1/internal*` and `/api/v1/webhooks*`
  by path. Express matches routes case-insensitively, so path variants are the API's job, and they
  are covered: the internal API needs the key (constant-time, `internal-api-key.ts`) and the webhook
  needs Meta's signature. Keep both; do not rely on the deny list alone.
- **ZIP bombs.** `zip-guard.ts` measures what really inflates, entry by entry from the local
  headers; the parsers read the central directory, which can disagree (overlapping-entry bombs). The
  conversion worker's heap and time limits (`document-converter.ts:48-57`) still bound it.
- **Webhook replay.** Meta signs no timestamp; replays are absorbed by the body-hash dedupe and the
  per-`wamid` dedupe. When the planned retention of `webhook_events` arrives, the `wamid` dedupe
  becomes the one that matters; keep it permanent.
- **Health route.** `GET /api/v1/health` is public and returns DB status and uptime. Acceptable.
- **Docker apt key.** `host-setup.sh:148-149` downloads Docker's key over HTTPS without checking its
  fingerprint (`9DC8 5822 9FC7 DD38 854A E2D8 8D81 803C 0EBF CD88`). Standard practice; one
  `gpg --show-keys` check would close it.
- **CSP `'unsafe-inline'`.** Documented decision (B+ on the demo, nonce CSP on a paid deployment).

## 3. Controls verified (no finding)

- **Sessions (ADR-018):** Argon2id 19 MiB / t=2 / p=1 with rehash on login, NFKC passwords, dummy
  hash for unknown e-mails; HS256 with `alg`, `iss`, `aud` and required `exp` / `iat` / `sub`; role and
  session re-read from the DB on every request; refresh tokens 256-bit, stored as SHA-256, rotated
  under `SELECT … FOR UPDATE`, reuse revokes the session; cookie `HttpOnly`, `Secure` (`__Secure-`),
  `SameSite=Strict`, path `/api/v1/auth`; CSRF = custom header + Origin allow-list +
  `Sec-Fetch-Site`; logout-all, deactivation and role change take effect immediately (SSE included).
- **Authorization:** every admin route declared in one table with its roles; the authz matrix is
  generated from the routes the app really serves (demo routers included) with invariants a
  regenerated fixture cannot hide; item-level review rules in a separate matrix; last-admin and
  self-demotion protections; public demo account refused for password, role, active, locale,
  logout-all and admin session revocation.
- **Webhook:** HMAC-SHA256 over the raw body, constant time, before parsing; verify token constant
  time; `phone_number_id` filter; 3 MB cap; own limiter; outbox + sweeper.
- **Files:** mime allow-list per message type, magic-byte sniffing, per-type size caps with streaming
  cut-off, converter in a worker thread with heap / time limits, ZIP guard, SheetJS tarball pinned by
  integrity hash; media served with `nosniff`, `default-src 'none'; sandbox`, CORP, attachment for
  anything not image / audio / PDF.
- **Demo mode:** fakes forced before validation; the production demo refuses to start with any real
  key pattern, an admin password, or a database not named `*_demo`; `assert_no_real_keys` repeats it
  in the deploy scripts; per-IP and global limits for samples and resets; SSE caps per IP for the
  shared account.
- **Logs:** `authorization`, `cookie`, `set-cookie`, signature and internal-key headers redacted;
  `hub.verify_token` redacted from URLs; phone numbers masked; Caddy redacts credentials by default.
- **CI / supply chain:** `permissions: {}` by default and per-job least privilege, every action pinned
  by SHA, tool images by digest, `persist-credentials: false` everywhere, no `pull_request_target` or
  `workflow_run`, fork PRs run only the read-only `quick` job, actionlint + zizmor, gitleaks on every
  push and weekly on the full history, `pnpm audit` gate with dated exceptions, Trivy, Renovate with
  minimum release age and no automerge.
- **Server:** secrets generated on the VM (`openssl rand`, `umask 077`, mode 600, checked before
  every deploy), version strings validated before use in commands, no `eval`, Postgres and n8n never
  published, SSH keys only, fail2ban, unattended upgrades, Docker logs capped (5 × 10 MB),
  append-only encrypted backups with the private key off the server.

Accepted exceptions still in force (checked, all justified and dated): 7 Perl CVEs in the Debian base
image until **2026-10-13** (Perl is never run), 4 npm advisories (postcss ×2, deepmerge-ts, mysql2)
until **2026-10-27** (build-time or never-loaded paths). None blocks publication; the Perl ones need
the new node digest within four days.
